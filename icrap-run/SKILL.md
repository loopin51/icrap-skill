# ICRAP 에서 코드 돌리고 검토하기

이 스킬은 **실행 → 검토 → 수정 → 재실행** 을 맡는다. 설치·로그인·종료 코드·비밀값·잡 제출 규칙은 `icrap` 스킬에 있다.
**`icrap` 스킬을 아직 읽지 않았다면 먼저 읽는다.** 모든 조작은 `icrap` CLI 로 한다(PATH 에 없으면 `~/.local/bin/icrap`).

## 1. 어디서 돌릴지 고른다

| 상황 | 경로 |
|---|---|
| GPU 학습, 몇 분 넘게 걸리는 실행, 실행 중인 워크스페이스가 없음 | **배치 잡**(기본) |
| 몇 분 안에 끝나는 확인, import·형상 오류, 짧은 반복 디버깅 | 실행 중인 **워크스페이스** |
| 비공개 저장소, push 할 수 없는 코드 | 워크스페이스만 가능 |

- 로컬에서 할 수 있는 확인(문법, 작은 입력으로 CPU 실행, 단위 테스트)은 로컬에서 먼저 끝낸다.
- 워크스페이스에서 **긴 학습을 돌리지 않는다.** `ws run`·`ws exec` 는 항상 시간 제한(기본 540초) 안에서 돌린다. 넘으면 잡으로 보낸다.

## 2. 배치 잡 경로

1. `icrap me` 의 `할 수 있는 일` 에 `잡 제출·취소` 가 없으면 사용자에게 쓰기 토큰 안내를 하고(`icrap` 스킬 0절) 워크스페이스 경로를 쓰거나 멈춘다.
2. `icrap` 스킬 1절 "제출 전에" 를 그대로 지킨다(공개 https 저장소, **push 는 사용자 확인 뒤** — 기본 브랜치가 싫으면 `icrap/<주제>` 브랜치를 제안,
   push 한 커밋 SHA, **짧은 시험 실행 먼저**, `&&`·`;`·파이프 규칙, `$RUN_DIR`).
3. 검토할 수 있게 코드가 찍게 한다: 시작 때 장치(`torch.cuda.is_available()`, GPU 이름), 주기적으로 스텝·loss·처리 속도, 끝에 최종 지표.
   지표는 `$RUN_DIR/metrics.json` 같은 파일로도 남긴다.

```bash
icrap job submit --name <주제>-r1 --repo <공개 https 저장소> --ref <커밋 SHA> --gpus 1 \
  --command 'nvidia-smi -L && python train.py --max-steps 50 2>&1 | tee -a "$RUN_DIR/stdout.log"'
icrap job wait <주제>-r1 --timeout 540     # Bash timeout: 600000. exit 0 완료(또는 시간 제한) · 3 실패
icrap job logs <주제>-r1 --tail 200        # 실행 중에도 된다
```

- 반복할 때마다 이름을 바꾼다(`-r1`, `-r2` …). 팀당 동시 2개뿐이니 한꺼번에 여러 개 던지지 말고 앞 결과를 보고 다음을 보낸다.
- 기다리는 동안 중간 로그를 본다. 처음 몇 스텝에서 이미 틀린 것(loss NaN, GPU 미사용)이 보이면 사용자에게 알리고 **확인을 받아** `icrap job cancel`.
- 폴링은 30초 미만으로 줄이지 않는다. `queued` 는 정상 대기다(다시 제출하지 않는다).
- 실패하면 `icrap job show <잡>` 의 `failure` 로 나누고 해당 컨테이너 로그를 읽는다(`icrap` 스킬 reference.md "잡 상태와 실패 사유").

## 3. 워크스페이스 경로

1. `icrap ws check` 를 먼저 돌린다. exit 3 이면 `icrap login --ssh` 흐름(`icrap` 스킬 0절, `--ssh` 가 셸 권한임을 한 문장으로 알린다), exit 4 면 관리자 문의.
2. 워크스페이스가 꺼져 있으면(SSH 명령이 `… 상태입니다` 로 exit 1) 자동으로 켜지지 않는다. 사용자에게 알리고 `icrap ws start <ws>`
   (쓰기 토큰 필요, 없으면 포털에서 켜 달라고 한다).
3. `ws run`·`exec`·`info` 의 종료 코드는 원격 명령의 것이다. 표준 오류에 `icrap:` 줄이 있을 때만 `icrap` 스킬의 종료 코드 표(1·2·3·4)로 읽는다.
   Bash 에 `timeout: 600000` 을 주고, `--timeout` 은 540초 이하로 둔다(`push`·`pull` 도 Bash `timeout: 600000`).

```bash
icrap ws info <ws>                         # 파이썬·torch·GPU·메모리·디스크(처음 한 번)
icrap ws push <ws>                         # 현재 git 저장소 → ~/icrap-run/<저장소>/src
icrap ws run  <ws> -- python train.py --max-steps 20
icrap ws run  <ws> --timeout 300 -- 'pytest -x -q 2>&1 | tail -n 40'   # 워크스페이스에서는 출력 줄이기용 | tail 이 괜찮다(아래)
icrap ws exec <ws> --cwd /shared/users/<내 이름> -- 'ls -la'
icrap ws put  <ws> ./config.yaml '~/icrap-run/<저장소>/src'
icrap ws pull <ws> '~/icrap-run/<저장소>/src/out' ~/icrap-results/<저장소>
```

- **따옴표 규칙**: `--` 뒤 인자가 여럿이면 각각 따옴표째 넘어가 원격 셸이 `*`·`$VAR`·`~` 를 풀지 않는다. `&&`·파이프·글롭·변수가 필요하면
  **따옴표로 묶은 문자열 하나**로 준다(`-- 'cd data && ls *.csv'`).
- `push` 는 `git ls-files` 기준이라 `.gitignore` 에 든 데이터·체크포인트·`.venv` 는 가지 않는다(200MiB 넘으면 멈춘다).
  보낼 때마다 원격 `src` 를 새로 만든다. **결과물을 `src` 안에 두면 다음 push 에 지워진다.** `pull` 하거나 `/shared/users/<내 이름>/` 으로 옮긴다.
- `run` 은 `src` 에서 실행하고 출력을 `~/icrap-run/<저장소>/logs/` 에도 남긴다(경로는 표준 오류의 `[ws] 로그:` 줄, 놓쳤으면
  `icrap ws exec <ws> -- 'ls ~/icrap-run/<저장소>/logs'`). 원격 종료 코드가 그대로 오고 `124` 는 시간 초과다.
- `run`·`exec` 의 명령은 `bash -o pipefail -c` 로 돌아 따옴표 안의 파이프(`| tail`)가 앞 명령의 실패를 지우지 않는다. 직접 `bash -c` 로 감싸면 그 안에 `set -o pipefail;` 을 먼저 둔다.
  (잡 명령의 파이프 규칙은 `icrap` 스킬 1절이다.)
- `pull` 의 로컬 대상은 디렉터리다(없으면 만든다). 저장소 밖이나 `.gitignore` 에 든 경로로 받고, 어디에 받았는지 사용자에게 알린다.
- 파이썬은 워크스페이스의 conda(Python 3.12)다. **torch 는 기본으로 없다.** `ws info` 가 `torch: 없음` 이면 설치(수 GB)를 사용자에게 먼저 묻고,
  아니면 배치 잡으로 간다.
- uv 프로젝트는 `.venv` 가 `src` 안에 생겨 **push 마다 지워진다.** `pip install -q uv` 를 한 번 한 뒤 `icrap ws run <ws> -- uv run python train.py …` 처럼
  `uv run` 으로 부른다(지워졌으면 다시 만든다). torch 가 든 의존성 설치는 540초를 넘길 수 있으니 torch 설치처럼 먼저 묻는다.
- 파일을 지우거나 덮어쓰는 명령, `/shared` 에 쓰는 명령은 사용자 확인 뒤에 한다. 백그라운드 프로세스(`nohup`, `&`)를 남기지 않는다.
- `icrap ws ssh` 는 대화형이라 Claude 가 쓰지 않는다. 사용자에게 자기 터미널에서 쓰라고 안내한다.
- GPU 워크스페이스는 확인이 끝나면 오래 붙잡지 말라고 알려 준다(정지는 사용자가 요청했을 때만).

## 4. 결과 검토

"완료" 상태만 보고 성공이라고 하지 않는다. 로그와 결과물을 **직접 읽는다.**

1. **끝까지 돌았나**: 종료 코드, 마지막 줄, 기대한 스텝·에폭 수, 결과 파일(`metrics.json`, 체크포인트).
2. **의도한 장치였나**: GPU 잡인데 `cuda: False` 거나 장치 로그가 없으면 CPU 로 돈 것이다(uv 의존성의 CPU 용 torch 를 의심한다).
3. **수치가 정상인가**: loss 가 NaN·inf 가 아니고 줄어드는지, 정확도가 우연 수준이 아닌지, 검증·학습 지표 차이. 처리 속도로 남은 시간을 계산해 72시간 한도와 비교한다.
4. **경고**: DataLoader worker, deprecated, 정밀도·장치 불일치, 메모리. 결과에 영향이 있는 것만 짚는다.
5. **재현성**: 커밋(`--ref`, `$RUN_DIR/commit.txt`)·명령·자원.

고칠 것이 있으면 로컬에서 고치고 → (잡이면 사용자 확인 뒤 커밋·push) → 이름을 바꿔 다시 돌린다.
같은 오류가 두 번 반복되면 멈추고 확인한 것을 보고한다. 원인을 추측으로 단정하지 않는다.

보고: 무엇을 돌렸나(경로, 잡·워크스페이스 이름, 커밋, 명령, GPU 장수) · 결과(상태, 핵심 지표와 근거 로그 줄) · 문제와 고친 것, 확인 못 한 것 ·
다음 제안과 결과물 위치(`/shared/runs/<내 이름>/<잡 이름>/`).

## 하지 않는 일

- 사용자 확인 없이 push, 잡 취소, 워크스페이스 정지, 큰 패키지 설치를 하지 않는다.
- 남의 잡·`/shared` 의 남의 폴더를 건드리지 않는다.
- 토큰·Coder 세션을 대화창에서 받거나 출력하지 않는다. `~/.config/icrap/` 를 읽지 않는다. `icrap login --paste` 를 대신 실행하지 않는다.
- 실패를 감추려고 테스트·검증 코드를 약하게 고치지 않는다.
